# S4.8 — Analyzer compute efficiency

Status: implementation and analyzer-specific acceptance complete. Integrated playback timing remains qualified only by the observations below; the strict whole-workload gate did not pass every run. This is local uncommitted source work, not a release or physical-device qualification.

## 1. Implemented sequence and contract

1. Prepare one worker-owned `EngineAnalysisPlan` at analyzer-thread entry using the engine's fixed sample rate, existing window length and logarithmic grid. Restart reconstructs the plan. The plan stores Hann weights, per-bin complex oscillator steps and coherent-gain/endpoint normalization.
2. Apply the Hann window and nonfinite-sample policy once per complete packet. Evaluate each frequency with double-precision oscillator recurrence instead of per-sample sine/cosine calls. Keep the original direct calculation as the independent test/benchmark reference. No FFT interpolation, frequency-grid change, smoothing change, or new audio behavior is introduced.
3. Retain selection/epoch checks before computation and publication, sequence-gap resets, stereo-mid capture, spectrum power averaging, spectrogram history and timing stamps. Producer paths still only assemble and enqueue complete windows; preparation and transforms run on analyzer consumers.
4. Publish lifetime consumer counters and transform wall-clock durations through `engine_get_analysis_diagnostics`. Measure matched reference/prepared CPU, then actual dummy-device playback with both consumers, with failures retained separately from analyzer correctness.

The same log-grid tonal peak-amplitude dBFS meaning remains: this is not noise density, integrated band energy, loudness, or true peak. Hann coherent gain, DC/Nyquist scale, silence floor, display clipping and nonfinite-input treatment are preserved within the measured numerical tolerance.

Each plan occupies 22,536 bytes; the transform has a fixed 16,384-byte double scratch array. Existing packet/history storage remains. There is no new heap allocation or render/callback transform work. Plans and scratch are private worker-stack storage with compile-time capacity checks for both production analyzer sizes (2,048×256 and 1,024×128). Per-window complexity remains proportional to frames × bins; this removes repeated transcendental work rather than changing the analysis definition.

Shared reuse: `reuse-deferred` for a new shared analyzer abstraction. The existing DAW packet queue and time mechanisms are retained; `core_math` has no matching calibrated arbitrary-frequency tonal-grid contract. DAW-specific grid, window, level and epoch policies stay in the engine. No shared source, version, dependency or adoption metadata changes.

## 2. Diagnostics semantics

The public snapshot reports queued, consumed, published, producer-dropped, stale-discarded, computed, approximate pending packets, consumer-observed backlog high-water, and total/maximum transform milliseconds. Stale includes rejection before computation and rejection after computation but before publication. Computed can therefore exceed published.

Counters/maxima are lifetime values for an engine instance. Pending reads the queue itself, so restarting/flushing a queue does not create a permanent false backlog from lifetime counter differences. Snapshots read atomics independently and are not a transaction: concurrent producer/consumer progress can change values between fields. Pending excludes a packet already being computed; an incoherent out-of-capacity read reports zero. High-water observes occupancy at consumer receive boundaries, not every producer write. Lifetime queue/consumer totals need not reconcile after a quiescent restart discards queued packets.

Transform durations use the monotonic performance counter and include scheduling/preemption during computation, but exclude preparation, queue waiting, power averaging and publication locking. They are elapsed time, not CPU time. The separate matched benchmark measures process CPU for each kernel. No diagnostics counter is added to the audio producer's existing capture loop.

## 3. Correctness and runtime checks

`test-analysis-calibration` compares all 13,824 bins from nine signal classes (silence, DC, Nyquist alternation, impulse, exact-grid and near-floor tones, deterministic noise, off-grid multitone and nonfinite input), both production window/grid sizes and 22.05/44.1/48/96 kHz against the original direct definition. Maximum observed absolute difference was **0.0000152588 dB**, under the explicit 0.002 dB gate. Existing independent level/endpoints/power-mean checks and actual worker publication tests continue to cover gaps, epochs, stereo cancellation and insert metadata.

Deterministic stalled-consumer capture verifies pending=2, then stale rejection without transforms; actual publication verifies transform counters/timing. The lifecycle test verifies bounded overflow and consumer diagnostics, five startup-failure stages, eight live restarts, and concurrent target/track edits. Normal and optimized checks, AddressSanitizer and ThreadSanitizer, the full stable and legacy suites, and final `make` passed. Their evidence is recorded in the implementation receipt. There is no allocation failure path for the fixed-storage plan.

## 4. Measured compute improvement

Three fresh processes per configuration, alternating original/prepared execution order inside each process, two warmup windows and twenty measured windows per kernel. Both kernels receive identical multitone samples. Profiles are sequential with no concurrent build; the host is not exclusive. Optimized measurements use `-O2`, no fast-math, assertions enabled.

| Window × bins | Rate | Original median | Prepared median | Median CPU speedup |
| --- | ---: | ---: | ---: | ---: |
| 1,024 × 128 | 44.1 kHz | 1.444 ms | 0.333 ms | 4.34× |
| 1,024 × 128 | 48 kHz | 1.425 ms | 0.331 ms | 4.21× |
| 1,024 × 128 | 96 kHz | 1.376 ms | 0.329 ms | 4.36× |
| 2,048 × 256 | 44.1 kHz | 5.513 ms | 1.330 ms | 4.14× |
| 2,048 × 256 | 48 kHz | 5.468 ms | 1.337 ms | 4.09× |
| 2,048 × 256 | 96 kHz | 5.358 ms | 1.330 ms | 4.03× |

These are medians of three within-process medians; CPU speedup compares matched aggregate CPU, not elapsed ratios. All eighteen optimized kernel cases improved CPU and passed numerical parity. Six additional unoptimized (`-O0`) 48 kHz comparisons, three per window size, improved CPU by 2.94–2.98× (about 66% less). The default application optimization policy is unchanged. Kernel gains are not whole-application CPU or GUI claims.

## 5. Live playback findings and S4.9 handoff

Every live case uses real SDL dummy callbacks, 128-frame blocks, a 32-block output target, 600 ms startup exclusion and four seconds of observation. Each FX track has Gain, Compressor, Delay and Limiter. These are bounded integrated probes, not sustained qualification.

- **32 FX tracks plus both analyzers:** six processes, three each at 48/96 kHz. All kept publishing and had zero dropped analyzer windows. Four failed the strict whole-workload gate: two had deadline misses without output gaps; two had output gaps of **896 frames at 48 kHz** and **5,376 frames at 96 kHz**, alongside deadline misses. The other two passed.
- **Matched 32-track playback with analyzers disabled:** six processes; four also had deadline misses, though all six had zero missing output. This establishes that deadline misses can occur without analyzer work; it does not establish the cause of the two enabled-case output gaps or prove analyzers cannot contribute under load.
- **Eight FX tracks plus both analyzers:** six processes; all had zero missing output and zero dropped analyzer windows. Five passed the strict whole-workload gate; one 48 kHz run had one audio-worker deadline miss. No threshold was relaxed and no failed sample was removed.

S4.8's calibrated compute optimization, worker ownership and backlog observability are complete. **Integrated deadline/underrun qualification remains open in S4.9.** Carry these failed runs into matched longer-duration scheduling/load investigation before claiming a reliable maximum track count. Also retain the existing long-session memory, recording/import/export/edit overlap, storage pressure, GUI and physical-device acceptance work. An FFT alternative is not warranted for this slice: the prepared existing transform already gives a measured substantial reduction without changing frequency semantics.

Raw successful and failed observations are retained in [the workload bundle](evidence/s4-analysis-workloads.json); source and verification identity are in [the implementation receipt](evidence/s4-analysis.json).

## 6. Reproduction

```sh
make test-analysis-calibration test-engine-analysis-lifecycle
make -f make/performance.mk performance-analysis performance-build
python3 tests/performance/run_analysis.py \
  --kernel build/performance/O2/targets/macOS-arm64/tests/analysis_compute_bench \
  --live build/performance/O2/targets/macOS-arm64/tests/runtime_workload_bench \
  --output /tmp/daw-analysis-new-run
```

Use a new output directory. `--controls-only` runs matched disabled-analyzer playback; `--live-only --tracks 8` selects the smaller enabled workload. The runner preserves logs and returns nonzero for any strict acceptance failure. Kernel speed is a measurement gate, not a host-independent stable-test assertion. The ordinary `runtime_workload_bench analysis` case now measures the prepared production kernel; `analysis_compute_bench` retains the old/new comparison. Build sanitizer and normal profiles sequentially and finish with `make`.
