## 1. Implemented sequence

1. **S4.7a: metadata and prepared adoption.** WAV probing shares structural validation with the decoder but skips sample payloads. Native MP3 metadata uses format/frame properties. Malformed WAVs cannot fall through to a permissive native metadata reader. Drag previews reuse library metadata. Cache adoption consumes private samples on success only; overflow, invalid descriptors and allocation failures preserve caller ownership. Unknown clip pointers are no longer freed by cache release. A prepared engine transaction never falls back to a decoder, even if its source file has disappeared.
2. **S4.7b: bounded owned jobs and cancellation.** One existing `core_workers` worker processes four DAW-owned slots. Admission counts queued, running and ready work. Worker callbacks return NULL; results never rely on an unowned/full shared completion queue. Cancellation reaches WAV reads, finite-value validation, native MP3 decode blocks, converter coefficient/output loops, content hashing and FFmpeg process waiting. Shutdown marks every slot canceled, drains the shared worker and releases results exactly once. Source device/inode/size plus nanosecond modification/change times are checked before preparation, afterward, and when control polls the result.
3. **S4.7c: project and destination lifetime.** The application owns an opaque import object; copied restore candidates borrow its pointer without taking ownership. Only successful project replacement increments its generation and cancels admitted work before destroying the old engine. Requests contain owned paths/IDs and a stable track runtime ID, never an engine or editable UI pointer. Deleted targets fail; shifted indices resolve by identity. New tracks are created only in the existing transactional insertion path. Publication preserves existing library no-overlap behavior, selection, inspector and clip undo commands. Recording/bounce use the same completion owner.
4. **S4.7d: workflows, residency and measurement.** Library scans defer both metadata probing and content hashing; a warm scan reuses metadata only for the same file version. Library drop, interactive recording finalization, and bounce insertion report pending/completed/canceled/failed outcomes. Ctrl/Cmd+Escape cancels pending imports. Successfully published WAVs survive cancellation, queue rejection or failed insertion. Warm imports skip decoding when a current-version source remains cached; if it retires before publication, the request returns to background preparation. Periodic control collection releases only render plans already retired by the worker, allowing inactive media to settle without another edit.

## 2. Ownership and memory policy

- `AudioMediaJobs` owns request/result slots; each result's sample buffer is private until main-thread adoption. Control alone mutates the registry, cache, engine, undo or UI.
- The default per-source and per-converted sample buffer ceiling is **64 MiB**. Four admitted jobs conservatively reserve at most **576 MiB** (two 64 MiB buffers plus 16 MiB converter allowance per slot). Actual ready sample bytes are reported separately; one decoder runs at a time. `audio_media_jobs_create(limit)` permits explicit caller selection; the application uses the documented default. This is an admission limit, not a resident-project limit or OS RSS guarantee.
- A file exceeding the decode limit fails insertion clearly. A saved recording/export remains on disk. The current default fits about 175 seconds of stereo 48 kHz float samples; higher rates/more channels fit less. Raising or exposing this policy and disk-streamed playback are separate decisions.
- Cache entries remain fully decoded and pinned by clips/render/export plans. There is **no inactive warm retention**: zero-reference entries are evicted immediately. Different source versions can coexist while old clips still pin prior bytes. Active project residency may exceed the preparation budget.
- Full-file synchronous APIs remain for explicit offline/raw callers and atomic restore. Interactive recording uses the application owner; raw/headless recording without that owner retains its original synchronous finish contract. Restore remains all-or-nothing, not incremental visible loading.
- Cancellation is cooperative between bounded CPU/read chunks. OS file/native codec calls are not hard real-time operations. FFmpeg cancellation kills and reaps the request-owned child and removes its temporary WAV. File version checks are observable filesystem identity checks, not a snapshot against arbitrary concurrent external file writes.
- File publication and insertion are distinct: `DawAudioRecordingResult.saved`, `.insertion_pending`, and `.inserted` describe those outcomes. Saving a project while imports are pending captures only its currently published clips. Shutdown cancels pending work before autosave; files already saved remain recoverable/importable.

## 3. Acceptance contracts

1. `test-media-preparation`: exact WAV metadata/samples, malformed/truncated rejection, every cache allocation failure, existing-key convergence, retain overflow, unknown-pointer ownership and zero-reference eviction.
2. `test-media-jobs`: fixed admission through ready state, byte rejection, changed-source rejection, queued/running/ready cancellation, source/converter checkpoints, shutdown retirement, plus native MP3 parity/budget/cancellation with a supplied fixture.
3. `test-media-import`: prepared insertion with the source removed, warm result with zero sample allocation and cache-miss retry, source versions with old pins, undo/redo, deleted/reindexed tracks, new-track cancellation, bounce completion, failed/successful actual session restore, warm metadata reuse and saved recording cancellation.
4. `media_ffmpeg_test`: real fallback decode plus deterministic sleeping-child substitution for cancellation, kill/reap and temporary-file cleanup. Substitution is test-only; the production fallback path performs the cleanup.
5. Optimized workloads: distinct 30-second stereo assets at 48 kHz and 44.1 kHz→48 kHz; cold/warm scans, cold/warm imports, three import/remove cycles, background preparation overlapped with eight FX tracks and real SDL dummy capture/output. Admission/poll cost, ready/reserved/pinned bytes, RSS and input/output/worker-deadline counters are separate observations.

The first workload exposed synchronous registry hashing and delayed retired-plan collection. Those findings were fixed before the accepted rerun; the initial failed measurement remains separately recorded. No threshold was relaxed to turn the failure into a pass. Residency is assessed after worker retirement and ordinary control collection, not while old render plans still legitimately hold pins.

## 4. Measured software workloads

Six fresh optimized processes passed: three native-rate and three converted-rate runs, each with four distinct assets, a warm batch and three removal/reload cycles. All six reported zero missing capture frames, zero missing output frames and zero whole audio-worker budget overruns. The intentional 200 ms main-thread consumption pause is included in batch elapsed time.

| Source rate | Cold batch median | Warm batch median | Maximum admission call | Maximum completion/drain poll |
| --- | ---: | ---: | ---: | ---: |
| 48 kHz | 300.42 ms | 229.25 ms | 0.359 ms | 2.255 ms |
| 44.1 kHz → 48 kHz | 1,182.79 ms | 232.65 ms | 0.280 ms | 2.389 ms |

The cold five-file scan cost 0.093–0.187 ms on control; warm scans cost 0.045–0.091 ms. Metadata/content preparation now occurs separately on the worker. The initial pre-fix cold scan had cost 101.30 ms because content hashing was still synchronous; this is one observed initial sample, not a universal speedup ratio.

Warm import results retained zero decoded sample bytes. After each retirement boundary, cache residency returned to the 11,520,000-byte bed-source baseline; ready/reserved job bytes returned to zero. Process RSS did **not** return to startup: final observed RSS was 151–187 MB versus about 68–80 MB before the workload. These process observations include allocator retention and other runtime storage; the receipt does not claim a zero-growth RSS bound or attribute all residual RSS to a particular owner. Long-duration/high-asset-count RSS qualification belongs to S4.9.

Raw observations and executable identity are in [the workload bundle](evidence/s4-media-workloads.json); [the implementation receipt](evidence/s4-media.json) binds source and checks. The initial failed ownership measurement is retained separately in [the initial sample](evidence/s4-media-initial-workload.json).
