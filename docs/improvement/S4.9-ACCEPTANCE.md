# S4.9 — Integrated sustained acceptance

Status: assessment completed on 2026-09-22; full sustained acceptance **not qualified**. This report records acceptance results without treating headless software checks as physical audio or hands-on UI acceptance.

## 1. Bounded execution sequence

1. Reproduce and characterize the S4.8 deadline/underrun observations with requested rate, observed callback cadence, busy-worker timing, queue depth, and analyzer throughput reported separately.
2. Run sustained playback with nominal wall-paced consumption and the existing SDL dummy driver, then a combined linear audio/MIDI/FX/analyzer/recording/import/edit/export workflow. Keep strict timing failures visible.
3. Check owned-media retirement and time-series RSS, finalize and insert recorded media, preserve canceled-export destinations, and save/reload the resulting project. Exercise existing storage/recovery fault checks rather than filling the host disk.
4. Bind measurements to the optimized executable/source, run relevant correctness and sanitizer checks, build the default app, and attempt an isolated visual startup artifact.
5. Reconcile S1–S4 state and identify the next visual/hardware and MCP-facing work. No commit, release, physical microphone operation, or new MCP server is included.

## 2. Measurement boundaries

The old SDL dummy runs can consume frames faster than their nominal sample rate; actual callback frames per wall second is now measured. A separate test-only consumer pauses the SDL output endpoint and calls the production callback on absolute monotonic deadlines. It records late wakeups and avoids catch-up bursts. That mode is an idealized nominal-rate software consumer, not hardware or a physical deadline guarantee. Production device and scheduler policies are unchanged.

The sustained mixed workflow uses the real SDL dummy output and input endpoints, linear playback, existing public control APIs and application import/recording owners. It alternates gain/pan, repeatedly inserts/removes imported converted media, adds/removes empty tracks, and performs streamed exports while recording remains active. A long take is finalized and inserted, then the resulting project is serialized and restored. Temporary fixture roots isolate user projects.

The strict timing gate retains both counters rather than equating them with audible failure. `worker_over_budget` measures a busy worker iteration against one nominal DSP block duration; the worker normally renders ahead into a queue. Such an exceedance is not itself proof that a queued callback missed its delivery deadline. The test-paced consumer's late wakeups are a separate scheduler observation. Missing input/output frames remain the direct software continuity failure counts.

## 3. Fixed workload matrix

All cases are fresh sequential optimized processes, no concurrent builds, stereo playback and a 32-block render-ahead request. Startup exclusion is 600 ms; configurations and actual durations are retained in receipts.

| Case | Wall duration | Purpose |
| --- | ---: | --- |
| 32 FX tracks, both analyzers, SDL dummy, 48 kHz / 128 | 60 s | Original workload extended with actual callback cadence |
| Same project, nominal wall-paced output, 48 kHz / 128 | 120 s | Separate nominal-rate demand from dummy cadence |
| Eight FX tracks plus MIDI, both analyzers, mixed workflow, 48 kHz / 128 | 120 s | Concurrent capture, converted imports, scalar/structural edits, streamed export and final project round trip |
| 32 FX tracks, both analyzers, SDL dummy, 96 kHz / 128 | 60 s | Higher-rate integrated pressure |
| Matching 96 kHz dummy case with analysis disabled | 60 s | Analysis-cost control |
| 32 FX tracks, both analyzers, nominal paced output, 96 kHz / 128 | 60 s | Nominal higher-rate demand |
| Matching 96 kHz paced case with analysis disabled | 60 s | Paced analysis-cost control |
| Mixed workflow, 48 kHz / 512 | 120 s | Larger-block integration comparison |

Playback fixtures reuse an eight-second stereo source; mixed playback arranges enough repeats to remain active throughout the accelerated dummy stream and adds a long MIDI note. Repeated six-second imports are converted from 44.1 kHz and placed beyond the active range, then removed. This tests ownership/publication under active playback, not a huge distinct-asset library. The separate S4.7 distinct-asset tests retain their own evidence.

Mixed workloads request gain/pan changes every 250 ms, imports about every five seconds, empty-track add/remove pairs about every ten seconds, and two-second streamed exports about every ten seconds. Export progress keeps recording drains active. Final recording publication is separate from asynchronous clip insertion; the resulting project is written/read/applied and recaptured to compare track/clip counts, region kinds/positions/durations, note counts and media paths. Export observers reject nonfinite/silent output; cancellation must preserve a byte digest of the existing WAV.

Owned-media retirement is checked before each fresh import and at the final retirement boundary. RSS is observed once per second and reported as process memory, not a proxy for live media ownership. Finalization/reload occurs after the steady interval and is not included in the steady RSS plateau claim.

A separate follow-up enables `DAW_BENCH_HEAP=1` to sample macOS malloc-zone bytes in use/reserved, before fixture construction, during the interval, after media retirement and after cleanup. This is an attribution probe, not part of the original timing matrix: allocator introspection can add locking overhead. It is used to distinguish a growing live heap from retained allocator pages when RSS rises. It does not prove that every external allocation is accounted for, and no allocator-purge workaround is applied to make RSS appear flat.


## 4. Results and disposition

The fixed matrix ran for 660 seconds of measured intervals in eight fresh processes. **8/8 workflow gates passed, 7/8 continuity gates passed, and 0/8 strict timing gates passed.** The runner correctly returned failure for the strict aggregate; short successful rehearsals do not replace these results. See [raw matrix and source manifest](evidence/s4-sustained-workloads.json) and [combined receipt](evidence/s4-sustained.json).

| Case | Output missing frames | Busy-worker budget exceedances | Paced late periods |
| --- | ---: | ---: | ---: |
| Dummy 32-track 48 kHz | 0 | 27 | 0 |
| Paced 32-track 48 kHz | 0 | 70 | 42 |
| Mixed eight-track + MIDI, 48 kHz / 128 | 0 | 18 | 0 |
| Dummy 32-track 96 kHz | **8,320** | 78 | 0 |
| Dummy 96 kHz, analysis disabled | 0 | 167 | 0 |
| Paced 32-track 96 kHz | 0 | 30 | 22 |
| Paced 96 kHz, analysis disabled | 0 | 169 | 92 |
| Mixed eight-track + MIDI, 48 kHz / 512 | 0 | 1 | 0 |

All enabled analyzers reported zero dropped windows. The heavy 96 kHz dummy case reached a 98.335 ms maximum busy-worker observation. These results do not isolate its cause or establish that disabling analysis solves it. Dummy callback demand was about 57k frames/s at requested 48k/128, 103k at requested 96k/128, and 45.5k at requested 48k/512. Nominal paced controls had no missing output, but retained late wakeups and budget exceedances. Counter deltas exclude startup; worker maximum values and paced late observations cover the consumer/engine lifetime, including warmup.

Both two-minute mixed cases completed 24 converted imports/removals, 12 streamed exports and 12 structural edit pairs. The 128-frame case performed 475 gain/pan edit pairs and finalized exactly 6,848,768 captured mono frames; the 512-frame case performed 474 and finalized 5,451,264. Neither lost input/output frames or analyzer windows. Both preserved canceled-export bytes and restored the resulting project. All 25 media-retirement checks per case returned to the 3,072,000-byte pinned baseline. Maximum control service batches were 77.456 and 72.355 ms, including synchronous export; these are not GUI frame-time measurements.

The 32-block target represents 85.33 ms of render-ahead at 48 kHz / 128, 42.67 ms at 96 kHz / 128, and 341.33 ms at 48 kHz / 512 before other latency. These are compatibility-buffered workloads, not low-latency qualification.

## 5. Memory follow-up

Process RSS grew from 58,015,744 to 225,624,064 bytes in the mixed 128 case and from 63,668,224 to 230,948,864 in the mixed 512 case. Returning pinned media to baseline does not establish a process-memory plateau.

A separately instrumented 180-second mixed run completed 36 imports, 18 exports, 18 structural pairs and 711 scalar edit pairs with no input/output/analyzer loss; 37 retirement checks settled to baseline. Reported malloc bytes in use during its last minute ranged from 48,440,720 to 54,470,096, while RSS ranged from 234,094,592 to 235,077,632. After finalization, restore and cleanup, reported malloc use was 5,920,928 bytes and RSS was 340,525,056. This narrows the investigation toward process/allocator residency beyond live pinned media, but neither proves all growth is allocator retention nor certifies long-session behavior. The ordinary matrix and heap-probe executable identities are separately retained because optional heap instrumentation was added afterward; production source was unchanged.

An independent ten-second `leaks --atExit` probe reported zero leaks and zero leaked bytes. Its scope and debugger warning are retained in the receipt. It does not certify the three-minute or overnight workload.

## 6. Visual boundary and remaining acceptance

The optimized real app opened isolated empty and populated synthetic projects and captured labeled 2560×1440 frames with dummy audio. The populated project includes the recorded take, MIDI and effect chain from the sustained run. Captures are in `visual_artifacts/s4.9/`; their hashes and executable identity are in the receipt. The initial isolated fixture omitted its font resource path; that geometry-only capture was rejected, the fixture was corrected, and both final captures verified loaded fonts. No production UI fix was made.

Visual inspection finds crowded and overlapping effect headings/controls, especially the compressor/limiter cards. This is concrete S5 work. A first frame does not prove interactive editing, analyzer animation, frame/input latency, waveform-cache completion, or physical sound. No hands-on user acceptance or real microphone/speaker test is claimed.

1. **T1 — Timing and device acceptance:** isolate high-load tail latency and qualify a chosen real device/rate/buffer. Preserve the observed 96 kHz gap as a failure until independently resolved or excluded by an explicit supported workload policy.
2. **M1 — Long-session memory:** distinguish allocator/mapped residency from owned allocations over longer realistic sessions, including repeated project replacement and recorded-media insertion. Full decoded active files remain a documented limit.
3. **V1 — Interactive product acceptance:** exercise one complete edit/record/export/reopen journey; measure UI responsiveness and fix visible feedback/history/layout failures. First-frame proof is only a starting point.

S4.9 closes this bounded assessment and leaves these acceptance findings open. No speculative scheduler rewrite, MCP implementation, default optimization change, installation, release or commit was performed. See [overall functionality and next steps](DAW-STATUS-AND-NEXT-STEPS.md).

The TSan run retained 41,216 missing output frames under instrumentation; its timing is excluded from performance qualification. The ASan run had no output/input gaps. Existing storage/recovery fault tests passed without forcing host disk exhaustion.

Reproduction commands and profile separation are documented in `tests/performance/README.md`. The matrix runner exits nonzero when strict timing fails and preserves every receipt. Builds and measured workloads were serialized. Shared governance reuses the existing DAW engine, jobs, queue and `core_time`; the nominal paced consumer is test-only, with no shared-library/version/adoption change.

Documentation reconciliation uses HEAD~1..HEAD, the current dirty worktree, source/measurement inspection and bounded older MemDB context. New receipts govern present status. No memory writes were authorized or performed. Final default build and documentation verification are recorded in the combined receipt.
