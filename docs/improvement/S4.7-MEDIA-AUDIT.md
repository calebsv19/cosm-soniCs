# S4.7 — Media preparation and cache audit

Historical audit: this plan preceded implementation. S4.7a–d are now implemented in [the media preparation report](S4.7-MEDIA.md); the findings below describe the earlier source state. S4.7 implementation was not included in the capture-clock fix. The clock follow-up is documented separately in [capture continuity](S4-CAPTURE-CLOCK.md).

## 1. What S4.7 builds on

S4.6 bounded recording/export output pipelines. It did not change decoded source ownership: inserting the resulting WAV still loads a complete asset into the engine cache. The capture-clock correction preserves already-anchored sample continuity while diagnostic snapshots are busy; it does not change media loading, caching, or project replacement.

S4.7 should make **media preparation responsive and lifetime-safe**, starting with existing WAV/MP3 decode and conversion. Disk-streamed playback of arbitrarily long assets is a separate architectural boundary because current samplers and export plans pin complete immutable `AudioMediaClip` buffers.

## 2. Current entry points and costs

| Entry point | Current behavior | Required change |
| --- | --- | --- |
| `src/ui/library_browser.c:library_resolve_duration_seconds` | Decodes a whole file just to obtain duration during library scanning | Metadata-only probing and cached file identity; expensive formats use an owned background probe |
| `src/input/timeline/timeline_drop.c:library_item_preview_duration` | Decodes/converts another temporary clip for drag duration, then frees it | Reuse duration metadata; drop previews must not trigger full decode |
| `src/engine/engine_clips.c:engine_clip_create_with_source` and `engine_clip_resolve_media` | Calls synchronous cache acquisition during clip preparation | Adopt a privately decoded asset on control, then perform normal transactional clip publication without reopening the file |
| `src/audio/media_cache.c:audio_media_cache_acquire` | Cache lookup, decode, allocation, identity update and retain happen together | Split lookup/retain from prepared-result adoption with explicit ownership on every failure |
| Recording Finish and bounce insertion | Publish a durable WAV, then synchronously import it | Submit an owned import request after publication; report file success separately from pending/failed insertion |
| `src/session/session_apply.c:session_apply_document` | Prepares a complete candidate, destroys the old engine and assigns `*state = *candidate` | Import lifetime/generation state must survive outside copied candidate state; reject results for retired projects before any engine/cache access |

The S4.1 historical optimized baseline measured a 30-second WAV import at 73 ms native rate and 294 ms for 44.1→48 kHz conversion. Those are earlier measurements, not fresh S4.7 performance results. Current source still runs those operations synchronously. New acceptance must measure distinct assets and preview/scan workflows, not only repeated references to one cached file.

## 3. Ownership findings

1. The cache is control-thread-owned and unsynchronized. Workers must decode into standalone `AudioMediaClip` values; they must not call cache acquire/release, modify tracks, publish engine revisions, update undo, or use mutable UI pointers.
2. Cache entries stay resident while referenced and are immediately evicted at refcount zero. There is no byte budget or inactive warm-entry retention. Prepared render/export plans take independent pins. Eviction must never reclaim pinned media; a warm-cache policy needs a separate retained-byte accounting rule.
3. Cache lookup keys use media ID or path plus target rate. Asynchronous requests also need owned path/ID strings, a source version/fingerprint, a project generation, and stable target-track identity. Track indices and an `Engine*` alone are insufficient across edits or project replacement.
4. `audio_media_cache_retain` guards `INT_MAX`, while the existing-hit acquire path increments without that guard. `audio_media_cache_release` frees unknown clip pointers. Before asynchronous adoption, unify retain overflow handling and make it impossible to send worker-owned/unadopted results through a cache release path.
5. WAV decode, native MP3 decode, FFmpeg fallback, and sinc resampling currently have no cancellation parameter. Background execution alone would still require waiting for long work during shutdown. Cooperative cancellation must cover bounded decode/conversion work and child-process cleanup, retaining existing format validation and exact output.
6. Completed but unadopted results consume memory too. Bound total admitted requests and decoded bytes across queued, running, and ready states; do not count only active worker threads. A canceled or stale result must release its privately owned buffer exactly once.

## 4. Proposed implementation sequence

1. **S4.7a — Separate probing, decoding, and cache adoption.**
   - Add duration/format probing without sample allocation for supported WAV structures; retain malformed/chunk-boundary checks.
   - Reuse metadata for scan/drag previews.
   - Add a control-only prepared-media adoption path with documented consume-on-success behavior; allocation failure leaves the worker result owned by its caller.
   - Prove native/converted sample parity, duplicate-key convergence, refcount boundaries, failed adoption, and no decoder call during adoption.
2. **S4.7b — Own background requests and cancellation.**
   - Introduce a bounded request store containing owned strings, source identity, target rate, project generation, stable track ID and insertion frame.
   - Start with one decoder worker; use cancellation checkpoints inside existing decode/resample paths and explicit cleanup for FFmpeg temporary files/processes.
   - Keep ready results in owned slots until control consumes them. Full capacity rejects admission clearly without losing task/result ownership.
   - Prove cancel before start, during decode/conversion, after completion, queue saturation, shutdown, and one-time resource release.
3. **S4.7c — Make publication survive project and track changes.**
   - Give the application an import-owner lifetime independent of the replaceable engine and copied restore candidate.
   - Advance/invalidate its generation on project replacement and shutdown; reject stale completions before dereferencing the old engine.
   - Resolve stable track identity on control, adopt media, then apply existing clip revision/undo behavior. Define cancellation or removed-target behavior before creating any requested new track.
   - Preserve S2 all-or-nothing project restore. Do not turn candidate preparation into partial visible session loading.
4. **S4.7d — Route user workflows and qualify memory.**
   - Route library drop first, then recording/bounce insertion, through the same import owner and pending/success/failure status.
   - Preserve durable-file success when insertion is canceled or rejected; do not silently discard a successfully saved recording/export.
   - Set explicit decode admission and optional inactive-cache byte budgets; active pins remain non-evictable. Report unavoidable pinned residency separately.
   - Measure distinct-asset cold/warm imports, repeated import/remove cycles, sample-rate conversion, scans/drags, and concurrent playback. Verify UI responsiveness and memory after jobs/results are retired.

These steps are ordered dependencies. S4.7a is the first implementation target; a worker should only be introduced once a decoded result can be adopted without synchronous re-decoding or ambiguous ownership.

## 5. Shared infrastructure decision

Existing DAW main-thread jobs run work on the UI thread and are not a decoder executor. The trace exporter already adopts `core_workers` and `core_queue`; reuse those existing dependencies where their contracts fit.

The current shared worker implementation pushes completion pointers without handling a full completion queue, and pending-cancel shutdown does not supply a task-context destructor. An import worker must not depend on that path to free large decoded results. A bounded DAW-owned request-slot store can keep task/result ownership, have worker callbacks return no completion pointer, publish ready slot state, and retire all admitted work through drain plus cooperative cancellation. This supports `reuse-adopted` for existing worker execution with DAW-specific lifetime policy; no shared extension is required by this proposal. Exact adoption should be verified when implemented.

## 6. Acceptance and reporting boundaries

1. Audio: native/converted WAV and supported MP3 output stays equivalent to the existing S3.5 decoder; malformed or unsupported input never partly publishes a clip.
2. Lifetime: queued/running/ready cancellation, repeated project replacement, deleted/reordered tracks, failed cache adoption, and full queues never access retired state or leak/double-free results.
3. Runtime: capture/playback remain active; report missing input/output frames, complete worker-budget overruns, UI event/poll cost, decode cost, and resident/ready/pinned bytes separately.
4. Memory: repeated imports and removals settle to the chosen policy. A complete active media library can exceed an inactive-cache budget; do not label full-file playback duration-independent.
5. Workflow: test pending insertion, completion, cancellation and failed insertion with preserved WAVs, undo, and project save/restore. Run stable/legacy, targeted sanitizers, measured workloads and final `make` at each implementation boundary.

No S4.7 performance gain, background loading, cache budget, or cancellation behavior is claimed by this audit. The existing source behavior and its limitations remain until these slices are implemented.
