# Collection-scoped project Load/Save

Main Edit's native Load and Save dialogs now show an explicit folder scope. The arrow buttons select one project directory at a time; the center collection-name button opens an editable collections-home path. Choose a home containing collection folders such as `classical_conversations/projects/` and `night_pocket/projects/`, or choose a collection folder directly. Load lists only valid regular JSON sessions from the selected projects directory. Supporting `brief.json`, renders, references, backups and symlink files are excluded. Empty collections remain selectable and available for saving.

The current Main Edit package advertises the existing canonical DAW `music_projects` folder as its initial browser home. `DAW_COLLECTIONS_ROOT` can explicitly override that browse-only default. This does not replace input/output/library roots. Other builds use `music_projects` relative to their working directory. Default and legacy project directories remain separate selector entries; externally loaded projects expose their current folder. Paths are displayed in each dialog. Browsing scope is retained for the app session; reopening a saved project can recover its folder independently of the initial collections home.

Selecting a collection changes only the visible project list and save destination. The current engine, song, undo history, project identity and startup markers remain untouched. Load, double-click or Enter explicitly opens the selected project through the existing transactional session loader. Cancel returns to the current song. Selecting a folder does not create a composition or copy assets. Save your desired checkpoint before explicitly loading another project; project replacement retains the existing application/history behavior.

Save always opens the native dialog. Enter or **Save new version** writes a complete project checkpoint in the selected scope. `Classical_Conversations` starts at `Classical_Conversations_v001.json`; `Classical_Conversations_v001_ThemeStudy` preserves its suffix and advances to v002, v003, and so on. The next number is greater than every matching existing filename, including malformed or reserved files. A preview shows the destination. A synced, validated candidate is published atomically with no replacement: concurrent filename collisions fail safely and can be retried. Failed saves retain the current song, name, path and prior project bytes.

**Update current** is a separate action that updates the current project's exact path, even when the browser points at another collection. The current path is also displayed. Existing validated backup and recovery semantics remain in force. Normal shutdown still autosaves the current named project at that same path; earlier separately saved versions remain independent checkpoints. Successful explicit saves/loads advance the usual startup markers. No marker or global data-root change is used to switch browsing scope.

The browser shows up to 66 folder scopes and the first 64 project names in lexical order. Version numbers are bounded below one million. Overlong checkpoint names, inaccessible directories and bundle-contained destinations are refused. Discovery is shallow: projects remain flat in each collection's `projects/` folder. No session schema or program version change is required. Project creation/open/save remain native operations; this slice adds no MCP project-file tools.

Verification covers scope isolation, empty folders, preserved song/markers, version suffixes and monotonic numbering, atomic no-replace collision handling, exact-path updates, validated save/reload with byte-identical MIDI audio, release-owned modal controls, folder cancellation, compact layouts and native Vulkan captures. The existing atomic-save failure/recovery suite and broad stable smoke lane are also used. Physical interaction remains a separate acceptance boundary.
