# Guarded MIDI arrangement

The common `daw_action_arrange` action and the local MCP tools `get_arrangement`, `arrange_regions`, `undo_arrangement` and `redo_arrangement` support arranging existing MIDI regions. They supplement region creation/extension and note editing; they do not create tracks implicitly.

1. Read `get_arrangement` to capture an `expected_arrangement` token and stable existing track/region placements. The token retains exact project generation, ordered track identities, placements, sample rate, complete tempo events, region names, notes, instrument settings and clip automation. Mixer settings, track names, effects and dedicated EQ are outside this guard because arrangement restoration does not replace them. Four independently owned captures are retained per endpoint.
2. Submit one through sixteen edits with the endpoint instance, a fresh request ID and the current token. `duplicate` and `move` take a MIDI-region `target`, canonical decimal `start_frame`, and an optional existing track `destination`. `trim` takes only its target and a shorter positive `duration_frames`. `delete` takes only its target. Unknown, repeated and irrelevant operation fields refuse the request.
3. Inspect `ok` and `code`. Accepted batches publish once and reserve one complete undo step before publication. `output_targets` follows input order, with null for deleted regions. Copies receive independent clip identities; redo preserves the accepted identities. An identical move or trim is a no-op without project history. After an uncertain transport response, query `request_status` with the original request ID and instance.
4. Use the returned current token for scoped history. Undo/redo consumes only an arrangement command at the shared cursor and refuses later unrecorded layout/tempo or affected-content edits. Selection is restored by input/output clip identities after successful history publication.

Placement uses half-open intervals: touching boundaries are allowed, overlaps are refused. A simultaneous swap is validated against the final batch rather than each intermediate position. Each input region may occur only once in a batch. Right-edge trim currently requires an untrimmed source and refuses losing any note; it preserves authored automation points, including points beyond the new right edge, so later extension can expose them again. It does not implement left-edge trimming, note rebasing or destructive note cropping.

Cross-lane copies and moves freeze an inherited source instrument's effective sound as explicit region settings. They use the destination lane's mixer and effects. Sound settings, notes and clip automation are deep copied; there is no shared mutable note storage. Deleting regions preserves the existing track, mixer and effect chain.

Capture and accepted-result bounds are 128 tracks, 256 total clips, 32,768 total MIDI notes and 65,536 clip automation points. The action refuses conflicting playback, recording, Test, bounce and authoring gestures. Candidate publication failure restores the original project and leaves history unchanged. Projects containing audio can be inspected, but arrangement edits on audio targets are refused by this surface.

Native timeline MIDI-only duplicate/delete uses the same common action, including its sixteen-region limit and overlap refusal. Audio and mixed selections retain the existing clip-content editor behavior. The MIDI editor footer **Arrange** button opens exact start/length frame fields and an existing destination lane number (starting at 1), with Move, Copy, Trim, Delete, Refresh and Close. The form retains its complete captured guard while fields are staged; external project edits refuse until explicit Refresh. Successful copies select the new region. Matching pointer release is required, text uses shared UTF-8 editing, and focus loss/project replacement/application teardown release snapshots. Compact panes require enlargement rather than enabling clipped controls.

`test-arrangement` verifies atomic duplication/movement/swapping/trimming/deletion, cross-lane inherited sound with exact production samples, independent IDs and automation, native selection/history, stale/busy/overlap/no-op behavior and injected reservation/publication failures. `test-mcp-arrangement` uses the official SDK and production bridge to verify 40-tool discovery, empty-project preparation, accepted batches, typed refusals, immutable receipt recovery, exact project audio reopening and read-only admission. Fixture acceptance does not establish installed-client registration or human listening acceptance.

Native staged-field tests and AddressSanitizer qualify exact moves/trims, copies/deletion, stale-state refusal, invalid text, matching release and focus cleanup. The actual Vulkan painter harness verifies form/moved/trimmed frames and enclosing clip preservation. An actual App_Run official-SDK run qualifies 40 tools, arrangement edits and scoped history/receipts together with expression/effects/library/composition, normal SDL shutdown/save, real restart and exact captured WAV parity against the final binary digest. This remains development-native evidence, without installed-client registration or physical listening/performance acceptance.
